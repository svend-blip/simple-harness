## bounded-task run (the actual measurement)

```
$ /usr/bin/time -f '%e' simple-harness run \
    --base-url http://127.0.0.1:11434/v1 \
    --model kimi-k3:cloud \
    --workspace /tmp/run013-scratch-sh/ \
    --permission read_only \
    --output jsonl \
    --prompt-file docs/comparative/bounded-task-prompt.txt \
    --max-turns 8
2.44   # wall-clock seconds (from the first run, model tried to call a `system` tool)
4.24   # wall-clock seconds (from the second run, model answered in text and completed)
```

The 2.44s run was the canonical measurement; the 4.24s run was a re-attempt
with a longer prompt that completed normally.

## Per-tool comparison (startup behavior)

- **Pi**: time-to-first-byte = 648ms (`time_to_first_byte=0.648s` from
  `pi/startup-timing.txt`; Pi's run captured stdout lines, which include
  the trust prompt dismissal and model response).
- **Whip**: time-to-first-init = 14ms (whip -bench exits in 14ms with
  config.load done); TUI time-to-first-byte not measurable in script(1).
- **Simple Harness**: time-to-first-byte = 1329ms (HTTP round-trip to
  endpoint + model start). The first non-event emitted is the `started`
  event at t=0, but the first user-meaningful output (assistant delta)
  arrives at 1329ms.

The 1329ms is dominated by HTTP round-trip + kimi-k3:cloud's first-token
latency. Simple Harness itself adds negligible overhead before that
(measurement shows the `started` event is emitted in <1ms after
invocation; the wait is the network + model).
